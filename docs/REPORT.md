# Studevo — доповідь про функціонування проєкту

**Тривалість:** 7–8 хвилин + 2–3 хвилини демонстрації.
**Мета:** показати, що це не макет, а робоча LMS з реальною архітектурою,
базою даних, ролями та перевіреними сценаріями.

---

## 1. Вступ (0:00–0:45)

> Studevo — це університетська система дистанційного навчання. Вона об'єднує
> три ролі: студента, викладача і деканат. Студент бачить свої дисципліни,
> здає лабораторні роботи та отримує оцінки. Викладач перевіряє ці роботи за
> рубрикою. Деканат керує групами, користувачами та дисциплінами, бачить
> аналітику, але не втручається в оцінювання.

Проєкт реалізований як **мікросервісна система**:

- frontend — React 19 + Vite;
- backend — NestJS + TypeORM + PostgreSQL;
- 5 мікросервісів і окремий API Gateway;
- Redis Pub/Sub для подій, SSE для реального часу;
- файли — локальний диск або S3/MinIO.

---

## 2. Архітектура (0:45–2:00)

```text
Браузер (React SPA)
        │
        ▼
API Gateway :3000  ── JWT, CORS, rate-limit, проксіювання
        │
        ├── auth-service :3003          → auth_db
        ├── course-service :3001        → course_db
        ├── assignment-service :3002    → assignment_db
        ├── audit-service :3004         → audit_db
        └── communication-service :3005 → communication_db
```

> Браузер не підключається до бази напряму і не знає про внутрішні сервіси.
> Він звертається лише до шлюзу. Шлюз перевіряє JWT і передає запит у потрібний
> мікросервіс. Кожен сервіс має власну базу — це принцип database-per-service.

**Навіщо так:**

- відповідальність розділена: авторизація, дисципліни, оцінювання, аудит і
  повідомлення не змішуються в одному коді;
- кожну частину можна окремо масштабувати та деплоїти;
- збій одного сервісу не руйнує всю систему;
- окремі бази спрощують контроль доступу до даних.

---

## 3. Ролі та можливості (2:00–3:00)

| Роль | Що може |
|---|---|
| Студент | бачити дисципліни й матеріали, здавати роботи файлом, переглядати оцінки, писати викладачу |
| Викладач | створювати матеріали та завдання, перевіряти роботи за рубрикою, виставляти оцінки |
| Деканат | керувати групами, користувачами, телефонами, дисциплінами, розкладом; переглядати відомості та журнал |

> Деканат **не може оцінювати** роботи. Це обмеження реалізоване не лише в
> інтерфейсі, а й на сервері: endpoint оцінювання доступний лише ролі
> `TEACHER`, деканат отримує `403`.

---

## 4. Ключовий сценарій: здача → перевірка → оцінка (3:00–5:00)

### 4.1. Здача лабораторної

> Студент відкриває «Завдання», обирає PDF або DOCX і натискає «Здати роботу».

Що відбувається далі:

1. Frontend формує `FormData` і відправляє
   `POST /api/assignments/:id/submit-file`.
2. Gateway перевіряє JWT і проксіює запит у `assignment-service`.
3. Контролер приймає файл через `FileInterceptor`, а особу студента бере з токена.
4. Сервіс:
   - перевіряє дедлайн і фіксує прострочення;
   - перевіряє дозволений формат файлу;
   - визначає групу студента із зарахування;
   - зберігає файл у сховище;
   - створює або оновлює запис у таблиці `submissions`.

> У базі одна робота на пару «студент + завдання». Це гарантує unique-індекс.
> Статус нової роботи — `READY_FOR_GRADING`, оцінка порожня.

### 4.2. Оцінювання

> Викладач відкриває «Оцінювання», вибирає роботу, вводить бали за критеріями
> та натискає «Виставити оцінки».

Що відбувається:

1. Frontend показує живий підрахунок суми та ECTS.
2. Запит іде на `POST /api/grading/grade`.
3. Сервер перевіряє кожен бал за рубрикою:
   - невідомий критерій — помилка;
   - бал більший за максимум — помилка;
   - сума більша за максимум роботи — помилка.
4. Далі застосовується **Strategy**:
   - `STANDARD` — звичайний розрахунок;
   - `LATE_PENALTY` — мінус 20% за пізню здачу;
   - `EXCELLENCE_BONUS` — +5 балів, якщо результат ≥ 90%.
5. У **транзакції** оновлюються дві таблиці:
   - `submissions`: статус `GRADED` і підсумковий бал;
   - `grades`: новий запис із критеріями, правилом і коментарем.

> Якщо на будь-якому кроці станеться помилка, транзакція відкотиться: не буде
> ситуації, коли статус змінився, а оцінка не збереглася.

### 4.3. Деканат

> Деканат бачить відомості та може експортувати CSV, але форма оцінювання йому
> недоступна. Якщо деканат звернеться до API напряму — отримає `403`.

---

## 5. Безпека (5:00–6:00)

- Паролі зберігаються як **bcrypt-хеші**, не у відкритому вигляді.
- Після входу видається **JWT** (HS256, термін дії 8 годин).
- JWT перевіряється **і на шлюзі, і в кожному сервісі** — defense in depth.
- Шлюз видаляє клієнтські заголовки `x-user-*` і підставляє дані з токена.
- Є обмеження спроб входу: 20 спроб / 5 хвилин на IP.
- RBAC визначає, які дії доступні якій ролі.
- Файл здачі може скачати лише власник, викладач або деканат.
- Усі входи, зміни та відмови пишуться в **audit-service**.

---

## 6. Дані та база (6:00–7:00)

- PostgreSQL, окремі бази для кожного сервісу.
- TypeORM: сутності описують таблиці, міграції — схему.
- `synchronize: false` — схема не змінюється випадково.
- `migrationsRun: true` — міграції застосовуються під час старту.
- Демо-дані створюються ідемпотентно: повторний запуск не дублює записи.

**Поточний демо-склад:**

| Дані | Кількість |
|---|---|
| Студенти | 8 |
| Викладачі | 3 |
| Деканат | 1 |
| Дисципліни | 4 |
| Роботи на перевірку | 5 |
| Оцінки в журналі | 7 |
| Академічні групи | 4 |

---

## 7. Патерни та якість (7:00–7:30)

- **Strategy** — три правила оцінювання.
- **Builder** — побудова завдання.
- **Decorator** — кешування та логування Course Service.
- **Repository** — робота з БД через репозиторії.
- **DI** — впровадження залежностей NestJS.
- **Міграції** — версіонування схеми БД.

Перевірки:

- **87 юніт-тестів** (18 файлів);
- **44 інтеграційні перевірки** `verify:lab3`;
- ESLint без помилок;
- збірка фронтенду та сервісів успішна.

---

## 8. Демонстрація (7:30–10:00)

1. **Деканат:** панель → «Студенти» (пошук, телефони) → «Дисципліни» →
   «Відомості» (режим перегляду).
2. **Студент:** «Завдання» → здати PDF → показати повідомлення.
3. **БД:** показати новий рядок у `submissions` зі статусом `READY_FOR_GRADING`.
4. **Викладач:** «Оцінювання» → бали за критеріями → «Виставити оцінки».
5. **БД:** показати `GRADED` у `submissions` і новий рядок у `grades`.
6. **Деканат:** «Журнал» — подія про оцінювання.
7. **DevTools → Network:** показати `Authorization: Bearer …`.

## Додаток A. Цифри для відповідей

- 1 frontend + 1 gateway + 5 мікросервісів.
- 5 PostgreSQL-баз.
- 87 юніт-тестів, 44 інтеграційні перевірки.
- 8 студентів, 3 викладачі, 1 деканат.
- 4 дисципліни, 5 робіт на перевірку, 7 оцінок.
- JWT HS256, термін дії 8 годин.
- Штраф за пізню здачу — 20%.
- Бонус за відмінну роботу — +5 балів.

## Додаток B. Можливі питання

| Питання | Відповідь |
|---|---|
| Чому мікросервіси? | Розділення відповідальності, окремі БД, незалежне масштабування |
| Де перевіряється JWT? | На шлюзі та в кожному сервісі |
| Чому `synchronize: false`? | Щоб не змінити схему випадково; тільки міграції |
| Як пов'язані сервіси? | HTTP через шлюз і Redis Pub/Sub для подій |
| Де зберігаються файли? | S3/MinIO або локальний диск |
| Як деканат не може оцінювати? | RBAC + `403` на `POST /api/grading/grade` |
| Що буде при збої? | Транзакція відкочується, дані не розсинхронізуються |

## Додаток C. Версія на 3 хвилини

> Studevo — LMS для студентів, викладачів і деканату. Frontend на React
> звертається до API Gateway, а той після перевірки JWT проксіює запити в п'ять
> мікросервісів. Кожен сервіс має власну PostgreSQL-базу. Студент здає
> лабораторну файлом — сервер перевіряє дедлайн і формат, зберігає файл і
> створює запис у `submissions`. Викладач оцінює роботу за рубрикою: сервер
> перевіряє бали, застосовує правило Strategy і в одній транзакції оновлює
> `submissions` та `grades`. Деканат бачить аналітику й відомості, але оцінювати
> не може — отримує `403`. Усе це перевірено 87 юніт-тестами та 44
> інтеграційними перевірками.
